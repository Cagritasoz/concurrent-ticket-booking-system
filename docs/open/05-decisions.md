| 2026-11-01 | **Inventory model:** Venue → Layout → Section (seated with seats, or standing with a capacity); Event (in one layout of its venue) → TicketTier (price, description; later rules) → **one `tickets` row per sellable unit**, linked to a seat for seated sections and to its standing section for general admission (updated 2026-11-17, see below). | 2026-11-01 | **Per-customer limits are enforced** with a counter row per (customer, tier), updated in the same transaction as the booking, with a database `CHECK (count <= limit)`. Two parallel requests from the same customer can't both slip under the limit, and the rows are per customer, so they don't become hot rows. (Updated 2026-11-23: events can have a limit of their own too, counted the same way per (customer, event), and passes per (customer, pass); see "Three per-customer limits" below.) |

| 2026-11-17 | **Venues:** UUID primary keys (`gen_random_uuid()`) for every table the API exposes; name and optional description; an international address (line 1, optional line 2, city, optional region and postal code, ISO country code), the same shape Stripe uses; optional latitude and longitude, set together; an IANA time zone, so event times can be entered and shown in local time; an optional capacity (maximum occupancy), checked at publish. Optional text is `NULL`, never empty: the `CHECK`s reject blank strings. (Updated 2026-11-22: the capacity moved to halls; venues gained a status and a version, see below.) |
| 2026-11-17 | **Layouts:** a venue has several layouts (e.g. concert with a standing floor, basketball, theatre setup). A layout has sections, each either seated (with seats labelled by row and seat) or standing (with a capacity). Every event uses one layout of its venue; a venue with only standing room has a layout with one standing section, so there is no "venue without layout" case. Publishing checks that standing tickets fit their section's capacity and the total fits the venue's capacity. (Updated 2026-11-22: layouts belong to a hall of the venue, and the total is checked against the hall's capacity, see below.) |
| 2026-11-19 | **sqlc v1.31.1** generates the Go code for queries, with pgx v5 as the driver. It is installed as a binary pinned to an exact version, like golangci-lint, not added to `go.mod` as a tool, so its many dependencies don't mix into the app's. The generated code is committed, so building and testing don't need sqlc; CI checks it is current with `sqlc diff`. Hand-written tests live next to it. |
| 2026-11-19 | **Generated Go types:** standard library types where they exist: `uuid.UUID` (Go's `uuid` package) for `uuid`, `time.Time` for `timestamptz`, pointers for nullable columns (`*string`, nil is `NULL`), and `*float64` for venue coordinates (map positions, not money, so float precision is fine). `:many` queries return an empty slice, never nil. |
| 2026-11-19 | **Transactions** go through `postgres.WithTx(ctx, pool, fn)`: commit when `fn` returns nil, roll back on an error or a panic, `fn`'s error returned unchanged. READ COMMITTED (Postgres's default); a read-change-write locks its rows with `SELECT ... FOR UPDATE`. |
| 2026-11-19 | **Database errors:** a broken constraint is recognised by SQLSTATE code and constraint name (`postgres.IsUniqueViolation`, `IsForeignKeyViolation`, `IsCheckViolation`), so each module maps its own constraints to its own errors; "not found" is `pgx.ErrNoRows`. The module errors themselves (e.g. venue not found) arrive with the services that return them (step 5). |
| 2026-11-19 | **Lists use keyset pagination** (`WHERE (sort key, id) > (last values) ORDER BY ... LIMIT`), not `OFFSET`: every page costs the same and rows added meanwhile don't shift pages. Venues are listed by name, then id, one status at a time, with an index on `(status, name, id)` (migration 1). |
| 2026-11-20 | **Module layers:** handler (`httpapi`) → service (e.g. `event.VenueService`) → sqlc queries → Postgres. No repository layer of our own: the generated `Queries` already is one, and Postgres code is tested against real Postgres, not mocks. |
| 2026-11-20 | **Services return the module's own types** (e.g. `event.Venue`), converted from the generated row in one function, so `httpapi` never imports a `...db` package and a new column doesn't change a service's API. Not found is a module error (`event.ErrVenueNotFound`), not `pgx.ErrNoRows`. |
| 2026-11-20 | **HTTP errors are RFC 9457 Problem Details** (`application/problem+json`, the format Spring Boot 3's `ProblemDetail` uses), the same for every endpoint; validation errors list each field's problem. **Validation errors are 400 Bad Request**, like malformed JSON; 500s carry no detail, which goes only to the log. Built in M1 step 5b. |
| 2026-11-20 | **Input validation lives in the service** (e.g. `event.VenueInput`), in plain Go, not in struct tags or the HTTP layer: every problem is reported at once as a `*event.ValidationError`, each with the field's path in the API's JSON (`address.city`). Text is trimmed; optional text that is empty after trimming becomes `NULL`, so `""` and a missing field mean the same. A `CHECK` that still fails in Postgres is a bug in our validation, so it is a 500, not a 400. Country codes are checked for their shape (two capital letters) only, not against the ISO list. |
| 2026-11-20 | **Time zones are checked with Go's IANA database**, which `cmd/ticketing` embeds (`time/tzdata`, about 450 KB), so it works where the system has none (Windows, minimal container images). |
| 2026-11-20 | **Request bodies are read strictly:** `Content-Type: application/json` (else 415), at most 64 KiB (else 413), unknown fields rejected and nothing after the object (400). The decoding error messages are our own, in JSON terms, because `encoding/json`'s name Go types. Create answers `201 Created` with a `Location` header. |
| 2026-11-20 | **List endpoints page with an opaque cursor:** `?limit=` (default 20, at most 100) and `?cursor=`, answered as `{"venues": [...], "next_cursor": "..." or null}`. The cursor is the last venue's sort values (name, id) as base64url JSON; clients only pass it back, so its contents can change. It is not signed: an edited cursor only starts the page elsewhere. The service fetches one row more than the limit, so `next_cursor` is null on the last page even when that page is full, and no total count is returned (it would need a count over the whole table on every page). Unknown query parameters are ignored, unlike unknown body fields. |
| 2026-11-21 | **Partial updates are PATCH with JSON Merge Patch** (RFC 7396, `application/merge-patch+json`; `application/json` is accepted too, since the body is the same). A field left out is kept, `null` clears it (a required field set to `null` is reported as missing), nested objects (`address`, `location`) are merged. No PUT. The body is first decoded as the create body, which gives the same checks and error messages, then into a type that records which fields were sent (`patchField`: left out / null / value). The service's `Update` takes a change function, applied to the current values inside the locked transaction, so the merge (an HTTP format) stays in `httpapi` and the rules, the lock and the write stay in `event`. Every successful PATCH sets `updated_at`, also one that changes nothing. (Updated 2026-11-22: a PATCH also needs `If-Match` and raises the version, see below.) |
| 2026-11-21 | **DELETE answers 204 No Content**, and 404 when no venue has the id, also for a second delete of the same venue. Deleting a venue also deletes its halls, their layouts and sections (see the next rows); an event will keep its venue from being deleted (M1 step 8). (Updated 2026-11-22: DELETE needs `If-Match`, and is meant for what nothing uses; used objects are archived, see below.) |
| 2026-11-22 | **Halls between venue and layout:** venue → hall → layout → section. A venue is the building (address, time zone); a hall is a room in it that can host events at the same time as the other halls (a cinema's screens, a convention center's halls, an arena's one main floor); a layout is one way to set up a hall, one at a time. A venue with one room has one hall. A hall has a name, an optional description and an optional capacity, the room's maximum occupancy; publishing an event (M1 step 10) checks its tickets against its hall's capacity. **The venue has no capacity of its own**: it would repeat what its halls say (a one-room venue's capacity is its hall's), and a building-wide limit across halls running at once is not something ticketing systems enforce. Ticketmaster and Eventbrite instead list each room as its own venue; cinema systems (e.g. Vista: cinema → screens) model rooms explicitly, which is what we need to serve cinemas and multi-room buildings, where one building's events should be found together and its address kept once. |
| 2026-11-22 | **Halls, layouts and sections tables** (migrations 2 to 4). A layout has a hall, a name and an optional description; its capacity is not stored, since it is the sum of its sections. A section has a layout, a name, a kind (`seated` or `standing`) and, only when standing, a capacity; a seated section holds as many as it will have seats (M1 step 7). The kind is `text` with a `CHECK`, not a Postgres enum type, so a new kind is a one-line change. **Names are unique per parent, ignoring case** (halls per venue, layouts per hall, sections per layout), with unique indexes on `(parent_id, lower(name))`; the services will map them to their own errors by index name. **Status and version columns** follow the lifecycle and optimistic-locking rows below: halls `active` / `archived`, layouts `draft` / `active` / `archived` (default `draft`), sections no status; all three a `version`. The hall and layout name indexes are partial (`WHERE status <> 'archived'`), so they can't find archived rows; plain indexes on `halls(venue_id)` and `layouts(hall_id)` serve the foreign keys (a cascading delete looks children up by parent id) and the lists. **The venue tree is deleted as a whole:** `ON DELETE CASCADE` from venue to halls, hall to layouts and layout to sections (like JPA's `cascade = REMOVE` on a `@OneToMany`), because each level has no meaning without its parent. Events and tickets will reference layouts and sections without cascade, so used ones can't be deleted. **Left out, compared with Ticketmaster or SeatGeek seat maps:** map geometry (shapes and coordinates for drawing the map), levels or zones grouping sections (ticket tiers group them for pricing), and a display order (sections are listed by name). Each can be added as a column later without changing what exists. |
| 2026-11-21 | **A hall's layouts are listed without paging** (also a venue's halls and a layout's sections), all at once, sorted by name ignoring case: each parent has only a few, so a cursor would add code for a list that never fills a page. A child never moves to another parent, so updates don't touch the parent's id. **Foreign keys and unique names are enforced by the insert or update itself, not checked beforehand:** a check before writing can't see a parent deleted or a name taken a moment later, so the database would have to refuse the row anyway. The service turns e.g. `layouts_hall_id_fkey` into "hall not found" and `layouts_hall_id_name_key` into "name taken". Field rules are still checked in Go first, with Postgres's `CHECK`s as the last line of defense. (Updated 2026-11-22: since parents have a status, creating a child also reads and locks its parent, see "Lifecycle" below; the foreign key and the unique index stay behind that check.) |
| 2026-11-22 | **Frontend:** TypeScript + React, built after M2 (both UIs need login): an admin UI first, then a customer UI that grows with M3 onward. The owner decides how it looks and works; Claude writes the code. The seat map is our own, drawn from our seat data, not a third-party service such as Seats.io: Seats.io also keeps each seat's status per event, which would be a second source of truth for exactly what this system exists to get right (holds and exactly one winner per seat). When the frontend runs on another origin, CORS must allow the `If-Match` request header and expose the `ETag` response header, or the browser hides it from the code. |
| 2026-11-22 | **Roles and ownership, Ticketmaster-style** (built in M2). Three roles: **venue managers** build and maintain venue maps (venue, halls, layouts, sections, seats) and set event-level kills, which depend on the room; **organizers** (promoters) create and run events, tiers, prices and publishing, and set admin holds (artist, sponsors, press); **customers** book. Both admin sides are companies, not single people, so M2 adds **organizations** (`venue_operator` or `organizer`) with **memberships** (a Keycloak user and their role in the organization). A venue belongs to one operator organization (`venues.operator_id`), and its managers see and change only their own venues. **A venue grants an organizer access** (`venue_access`: venue, organizer, granted by, granted at, revoked at) before the organizer's staff can create events in its active layouts; revoking blocks new events, existing ones stay. An event belongs to its organizer (`events.organizer_id`). Keycloak keeps identities and global roles; organizations, memberships and grants are business data in our database, checked by the services (I13). **Simplification:** real venues grant dates (a calendar of holds on dates), not the whole venue. (Updated 2026-11-23: the venue also confirms each event's date and layout, see "Event lifecycle" below, which replaces the "whole venue" simplification for dates.) Until M2 the admin API is open and these columns don't exist; M2 adds them by editing the M1 migrations if M1 isn't merged yet, otherwise with new migrations. (Updated 2026-11-23: M1's tables reach `main` with its first part, so M2 adds these columns with new migrations.) |
| 2026-11-22 | **Lifecycle: archive instead of deleting what was used** (like Stripe products or GitHub repositories). Venues and halls are `active` or `archived`; layouts `draft`, `active` or `archived` (a layout is built over many requests and can't be chosen for an event until it is activated). **`DELETE` really deletes, only what nothing uses**; once events exist, their foreign keys (without cascade) refuse it, and the service answers 409 "archive it instead". **Archive and restore** are their own requests (`POST /{resource}/{id}/archive`, `/restore`), not a `status` field in PATCH, like Google's API design guide's custom methods. An archived object stays for history (past events, tickets and refunds point at it), is hidden from the default list (`?status=archived` lists them), can't be changed and gets no new children; archiving is refused while upcoming events depend on it (M1 step 8). Status changes are **compare-and-set** statements (`UPDATE ... WHERE id = $1 AND version = $2 AND status = 'active'`): when nothing matched, the service reads the row once to say why (not found, other version, wrong status). The children of an archived parent count as archived without their own rows being written. Creating a child reads and locks its parent (`SELECT ... FOR SHARE`) to check it is active. Name uniqueness ignores archived rows (partial unique indexes, `WHERE status <> 'archived'`), so a name can be reused. **Sections and seats have no status:** they are part of their layout's definition, edited while it is a draft. A layout used by a published event is frozen; "frozen" is derived from the events, not stored. Built for venues; the other tables have the columns (migrations 2 to 11), and their queries follow as each is built. |
| 2026-11-22 | **Optimistic locking with ETags on every admin change** (like JPA's `@Version`). Every table an admin changes has `version integer NOT NULL DEFAULT 1`, raised by 1 on every change (not `updated_at`, which repeats within a transaction, and not Postgres's internal `xmin`). Responses with one object send it as a strong `ETag` (`"3"`); lists carry `version` in each item instead. PATCH, DELETE, archive and restore **require** `If-Match` with that ETag: another version is `412 Precondition Failed` (read again, redo the change), a missing header or `*` is `428 Precondition Required` (a change must name what it is based on; `*` would mean "overwrite whatever is there"), and anything that isn't one ETag as the API sends it (unquoted, weak `W/`, a list) is `400`. Creates need none. Each object has its own version: changing a section doesn't raise its layout's. Tickets are the exception: admins change them in bulk (hold or kill many at once) with the event locked, so they have no version. Requiring the header is stricter than most public APIs (Azure and Google Cloud make it optional; Kubernetes requires a `resourceVersion` on updates); it fits an internal admin API whose one client, our UI, always has the version. In the service, the version check protects a person's edit; the row lock (`FOR UPDATE`) still protects the read-change-write inside one request. |
| 2026-11-22 | **Migrations are edited until their milestone merges into `main`**, then never again; later changes get new files. Before the merge only throwaway databases (tests, CI, a developer's local volume, which is recreated) have run them, and a table's whole structure stays readable in one file. (Updated 2026-11-22: one table per migration, see below. Updated 2026-11-23: a milestone now merges in parts, so the rule is per migration: edited until it is on `main`, see "A milestone in several pull requests" below.) |
| 2026-11-22 | **One migration per table**, with its indexes, named `NNNNNN_create_<table>`: 1 venues, 2 halls, 3 layouts, 4 sections, 5 seats, 6 event series, 7 events, 8 ticket tiers, 9 ticket types, 10 tier prices, 11 admin holds, 12 tickets, 13 passes, 14 pass prices, 15 pass events. A table's whole structure is read in one file, and the order of the files is the order of the foreign keys. A table added later gets the next number; until M1 merges, a change to a table edits its file. (Updated 2026-11-23: migrations 1 to 15 merge into `main` with M1's first part, so after that a change to one of these tables is a new migration, such as `000016_add_events_organizer_id`.) |
| 2026-11-22 | **Everything M1 stores is designed as tables first** (M1 step 6a: the venue tree, events, tiers, admin holds and tickets), before any of it is built end to end: building sections end to end and adding seats afterwards would mean changing finished code, and the relations are easier to review together. The generated Go code follows the review (`make generate`); until then `sqlc diff` reports it as out of date. |
| 2026-11-22 | **Seats** (migration 5) belong to a seated section, with text labels as printed on the ticket (`AA`, `12A`) and integer **row and seat positions** for the order (labels don't sort: `AA` after `Z`, `10` before `9`) and for finding seats next to each other later ("best available"); seats side by side have consecutive positions, gaps allowed. A section can't have two seats at one position or with the same labels (ignoring case). **Seat attributes:** a type (`standard`, `wheelchair`: a space for a wheelchair, often without a fixed seat, or `companion`: next to a wheelchair space), a restricted or obstructed view with an optional note (e.g. "pillar"), and an aisle flag. Real platforms show these on the seat map and in filters, and accessible seating has legal rules (e.g. the ADA in the US); which tiers may sell accessible seats, and releasing unsold ones to general sale, are tier rules (M1 step 9 and later). **Only seated sections have seats, checked by the database:** seats reference sections by `(id, kind)` with a `section_kind` column fixed to `seated`, so a seat can't be added to a standing section and a section with seats can't turn standing. Like sections, seats have a version but no status; what varies per event (tier, held, killed, sold) is on the event's tickets and their bookings (migration 11, M3). |
| 2026-11-22 | **Events** (migration 7) take place in one layout and reference it **without cascade**, so a layout, hall or venue that an event uses can't be deleted, only archived. The layout is referenced, not copied: a layout used by a published event is frozen (sections and seats can't change; an admin copies it to change it, M1 step 11), the event's own inventory is its tickets, and what a customer bought is copied into the booking when it is confirmed (M3), so later renames don't change past tickets. An event has a name, an optional description, a start and an end (instants, shown in the venue's time zone; the end is required, since it is when the hall is free again), an optional door time, an optional **on-sale time** (`on_sale_at`, before the start: like Ticketmaster or Biletix, an event is announced first and sales open at a set time, so customers see the event and its seat map before they can buy; without one it is on sale once published; bookings check it in M3; per-tier sales windows such as presales are left for later), a currency (every price of the event is in it, since one payment has one currency) and a status: `draft` (tiers, prices and tickets editable, nobody can book, can be deleted), `published` (visible, on sale from the on-sale time) or `cancelled` (was published; refunded in M7), with `published_at` and `cancelled_at` that `CHECK`s keep in line with it. **Upcoming** means published with the start still ahead; it isn't stored, since it changes with the clock. Archiving a layout, hall or venue is refused while it has upcoming events; draft events in an archived layout can't be published until they move or it is restored. **Two events in one hall can't overlap**, whichever of its layouts they use, since a hall is set up one way at a time (cinema and venue scheduling systems refuse double bookings too): an exclusion constraint over `hall_id` and `[starts_at, ends_at)` (with Postgres's `btree_gist` extension) refuses it, so back to back is fine; drafts count, so a draft keeps its slot and publishing can't fail on a clash found late; cancelled events don't. For that the event stores its `hall_id`, kept equal to its layout's hall by a foreign key on `(layout_id, hall_id)`. Changeover time between events (cleaning, setup) is not modelled. The venue isn't stored (it follows from the hall); `venue_id` is added if queries need it. The organizer (`organizer_id`) comes in M2. (Updated 2026-11-23: `published` is now `announced`, drafts no longer take the slot, changeover time is modelled, and sales get a closing time; see "Event lifecycle" below.) |
| 2026-11-22 | **Ticket tiers, ticket types and prices** (migrations 8 to 10). Real platforms price a ticket by two things: **where** it is (a price level) and **who** it is for (a ticket type), so one seat can be sold as Adult for 450.00 or Student for 300.00. **A tier** is the where: it belongs to one event and has a name (unique per event, ignoring case), an optional description, a **kind** (`seated`: the customer picks seats; `standing`: a quantity) and an optional per-customer limit over all its ticket types (enforced by the booking rules in M3). What it sells is its tickets (see the next row). **A ticket type** is the who: per event, a name (`Adult`, `Student`, `Child`; unique per event, ignoring case) and an optional description of who qualifies, checked at the door; a simple event has one, e.g. `Standard`. **`tier_prices`** is the matrix between them: one price per tier and ticket type, as integer minor units (`bigint`) of the event's currency, 0 for free, with a version like other admin rows; a type without a price in a tier isn't sold there. Integers, not `numeric`: exact, what Stripe takes, and plain `int64` in Go; rates (fees, VAT) will be rounded to minor units once, explicitly. Foreign keys over `(id, event_id)` keep a price's tier and type in one event. The customer picks the type when booking, so a ticket has no type; the booking records the type and its price (M3). Left to the services: every tier has at least one price when the event is published. Enforced tier and type rules (sales windows, presale codes, limits per type, a child needing an adult) and multi-event passes stay for later, as tables next to these. |
| 2026-11-22 | **Tickets are created when tiers are given seats and places**, not at publish (this replaced a first design with `tier_seats` and `tier_standing_places` tables turned into tickets at publish, which would have kept which tier sells a seat in two places once organizers move seats between tiers after publishing). Putting a section's seats in a tier inserts one ticket per seat with `INSERT … SELECT` from seats; moving a seat changes its ticket's `tier_id`; giving a standing tier 500 places of a section inserts 500 tickets with `generate_series`, and lowering it deletes available ones. Real platforms likewise build an event's inventory first and assign price levels on it before sales open. A draft's tickets can't be booked (bookings need a published event that is on sale); publishing is checks and a status change. A draft's tickets block deletes like any event's (of the event, and of the seats and sections they use), so the service deletes them first when it deletes a draft. |
| 2026-11-22 | **Tickets** (migration 12): one row per sellable unit (a seat, or one place in a standing section), in one tier. A ticket has its event, tier, kind, section and, when seated, its seat; foreign keys over two or three columns keep them consistent (the tier of this event and kind, the section of this kind, the seat in this section, the hold of this event), one ticket per seat and event is a unique index (which also means a seat is in at most one tier of an event), several tiers can share a standing section, and **nothing a ticket points at can be deleted**. Two rules are left to the services, checked with the event locked (the database would need the layout on every ticket, a three-column key on sections and another index on the largest table): a ticket's section is in the event's layout (so a draft's layout changes only while it has no tickets), and a standing section's tickets of all tiers fit its capacity. Its **status** is the admin's: `available`, `held` (by an admin hold, `hold_id`) or `killed` (removed from sale for good, e.g. a camera position). Whether it is sold is not a ticket column: booking items (M3) say so, with the "one active booking per ticket" index (I1). Tickets change in bulk with the event locked (I14), so they have no `version`. Indexes serve the known queries: a tier's available tickets (standing bookings take any of them with `SKIP LOCKED`), a section's tickets in an event (the seat map), a hold's tickets. |
| 2026-11-22 | **Admin holds and kills** (migration 11, decided from the open item): per event, not per layout, because the same layout hosts different productions. **A hold** (`admin_holds`: event, name, reason `artist` / `promoter` / `sponsor` / `press` / `accessibility` / `other`, optional note, version) keeps tickets out of public sale until an admin releases them to sale or books them for that party, usually placed while the event is a draft, before sales open; its tickets point at it, and a hold with tickets can't be deleted. **A kill** is only a ticket status, with no row of its own. Both keep the ticket's seat and tier, so a release is one update, and changing them takes the event's lock like other admin edits (I14), so a held or killed ticket can't be in a booking at the same time. Called **admin holds**, so they aren't confused with the short customer holds of M3 and M5. |
| 2026-11-23 | **What can change after publishing** (now: after announcing) (decided from the open item, built in M1 step 11). Real platforms keep rescaling while they sell (unsold seats move to another price level when sales are slow, holds are released, a late camera position is killed), so a published event's inventory stays editable, **except tickets that are sold**. A ticket counts as sold while a booking has it that is held (pending payment) or confirmed, the same "active" as I1; expired and cancelled bookings free it. After publishing, admins can: change names and descriptions; move unsold seats between tiers; hold, release and kill unsold tickets; add seats and standing places to tiers; add tiers and ticket types; change prices. A sold ticket is never moved, held or killed: its booking is cancelled and refunded first (M7). **A bulk change that includes a sold ticket is refused as a whole** and names those tickets, so a request either fully applies or not at all. **Removing inventory from a published event kills tickets instead of deleting them** (a ticket with booking history can't be deleted anyway, and one rule is simpler than two); raising a standing quantity revives killed places of that tier first, then inserts new ones up to the section's capacity. **A new price applies to new bookings only**: bookings copy their price (M3), so held and confirmed ones keep theirs. A ticket type with bookings can't be removed, and a tier can be deleted only once it has no tickets (its tickets are moved or killed first). The layout stays frozen (an admin copies it to change the room), and the date stays fixed (postponing is settled with cancellations, M7; updated 2026-11-23: a new date is now a reschedule, see "Event lifecycle" below). **No schema change**: tickets already allow these updates, and the service checks "sold" with the event locked (I14), using M3's active-booking index (I1). |
| 2026-11-23 | **Event series** (migration 6, built): a series groups events sold and shown as one production (a film's showings, a theater run, a season's home matches, a festival's days); `events.series_id` is optional, and a series with events can't be deleted (no ON DELETE). Tiers, ticket types and prices stay per event, because showings of one production are often priced differently (matinees, derbies); setting up a showing like an earlier one is a "copy setup" action in the service (M1 step 8 or later), not a shared row, as performing-arts systems copy a price map per performance. No status: a series is visible through its published events. It is cheap (one table, one nullable column) and it is what passes belong to. The later migrations moved up one number (events are now 7, tickets 12), allowed because M1 hasn't merged. |
| 2026-11-23 | **The whole domain is mapped before it is built** ([12 · Domain model](12-domain-model.md)): what each core table's row means is fixed now, so later features are new tables and nullable columns. Settled there; passes and `sold_as` are built (see below), the rest comes in later milestones: **passes** (`passes`, `pass_events`, `pass_prices`) belong to a series and grant one ticket in each of its events, taken from a tier named for the pass in each event, so passes have no inventory of their own and can't oversell single tickets; a seated pass takes the same seat in every event, so its events share one layout (updated 2026-11-23: or copies of it, see "Physical seat keys" below); a pass has its own price list, and each booking item gets an allocated share of the pass price so one cancelled event can be refunded alone. **Tables and boxes** are each their own section, and `ticket_tiers.sold_as` (`seat` or `section`) says whether a tier sells its sections only whole, per event. **Bookings are orders**: no `event_id` on `bookings`, since a pass booking spans events; per-event rules are checked through the items. **The ticket a customer gets** (a PDF with a signed QR code, emailed through the outbox after payment) needs no table; scanning once at the door adds `check_ins` later. |
| 2026-11-23 | **Passes** (migrations 13 to 15, built; sold once bookings exist, M3). `passes`: a product of one series (no ON DELETE), with a name unique per series, a kind (`seated` / `standing`), a currency, its own optional per-customer limit (separate from the tiers' limits) and `on_sale_at`, and a lifecycle like an event's (`draft`, `published`, `cancelled` with matching timestamps; updated 2026-11-23: `draft`, `announced`, `cancelled`), so a pass is set up hidden, then sold. `pass_prices`: its own price options (Adult 1,300.00), since ticket types belong to one event; the price is set by the organizer, never computed from the events' prices, so a pass can be a deal. `pass_events` (renamed from `pass_tiers`, which suggested a pass had tiers of its own): for each event a pass covers, the tier its ticket comes from, either a quota tier of its own or a tier shared with single tickets. It copies the pass's series, currency and kind so that three composite foreign keys keep every covered event in the pass's series and currency and every tier in its event and of the pass's kind; the same keys stop a covered event from being deleted, leaving the series or changing currency, a used tier from being deleted, and the pass from changing series, currency or kind. **Seated passes** choose seats by `seat_selection`: `same_seat` (one seat picked once, in every event, a season ticket; every event in one layout, or copies of it since the same day) or `per_event` (a seat picked or assigned in each event, so events can be in different layouts, halls or venues). **Tiers say who sells them** (`ticket_tiers.sold_via`): `single` (on its own, the default), `pass_only` (a pass's quota, with no prices of its own) or `shared` (both); `pass_events` copies the tier's `sold_via` into its foreign key (ON UPDATE CASCADE) and allows only `pass_only` and `shared`, so a `single` tier can't be a pass's tier and a used tier can't go back to `single`. **Tiers also say how they are sold** (`ticket_tiers.sold_as`): `seat` (the default) or `section` (each box or table, its own section, only whole; enforced when booking, M3). A tier sold as whole sections is sold on its own (`ticket_tiers_section_sold_alone`: `sold_via` must be `single`), because a pass takes one ticket per event and would break a table up; season boxes would be a product of their own. For such a tier `per_customer_limit` counts sections, and the service keeps each of its sections in that one tier (M1 step 9). Left to the service: a `same_seat` pass's events share one layout or copies of it (copying the seats onto passes to check it in the database isn't worth it for one mode), a pass is sold only while its events are on sale (updated 2026-11-23: while they are announced, by the pass's own sales times), and at publish every `single` or `shared` tier has a price and every `pass_only` tier is used by a pass. |
| 2026-11-23 | **Physical seat keys** (`seats.physical_seat_key`, migration 5). A seat row belongs to one layout, so a layout copy (M1 step 11) has new seat ids for the same physical seats. Each seat carries a key for the physical seat it is: a new seat gets a new random key, a copied seat keeps the key of the seat it was copied from. A `same_seat` pass then finds a holder's seat in events of different copies of the layout (a club fixing its stadium layout mid-season doesn't break its season tickets), and one broken seat can be killed in every layout of its hall. It is a shared value, not a foreign key, since there is no table of physical seats; a layout made from scratch gets new keys, so the way to give a new setup the same seats is to copy a layout and change it. Real systems keep a stable seat identity across map versions in the same way. |
| 2026-11-23 | **Ticket types and pass price options have a visibility**: `public` (customers can pick it, the default) or `admin` (only admins, never shown to customers). Without it, a complimentary "Comp 0.00" type for a hold's guests, a box-office rate or a free invitation pass would be open to every customer. A type unlocked by a presale code becomes a third value when codes are built. |
| 2026-11-23 | **Three per-customer limits**, each optional, each counted over the customer's held and confirmed bookings (M3), and a booking must keep within every one that applies: **the event's** (`events.per_customer_limit`, "6 per customer"): single tickets of the event, of all tiers together; **the tier's** (`ticket_tiers.per_customer_limit`): single tickets of that tier, "of which at most 2 VIP"; or sections, for a tier sold as whole sections; **the pass's** (`passes.per_customer_limit`): passes. A pass's tickets count only toward the pass's limit, not toward the limits of the events and tiers they come from, so each product's limit means one thing; tiers sold as whole sections count only toward their own limit (in tables), since a table of 8 would otherwise break a limit of 6 tickets. Real platforms put the limit on the event (Ticketmaster shows one per event) and sometimes a lower one on a price level. A tier limit above the event's limit is allowed but has no effect; the admin UI can warn about it. |
| 2026-11-23 | **Event lifecycle** (migration 7; replaces `draft` / `published` / `cancelled`, whose "published" hid three things at once: public, committed and sellable; where earlier entries say "publish", read "announce"). `draft` (the organizer prepares it, private, doesn't take the hall's slot) → `submitted` (the venue is asked for the date and layout; takes the slot) → `confirmed` (the venue agreed; the layout freezes here, since the venue agreed to that setup) → `announced` (public; single tickets sell between `on_sale_at` and `off_sale_at`) → `cancelled` (only an announced event; refunds in M7). Each step has its time (`submitted_at`, `confirmed_at`, `announced_at`, `cancelled_at`), and `CHECK`s keep them in line with the status and in order. A declined event goes back to `draft` with a `decline_reason`; a withdrawn one too; anything not yet announced can be deleted, since nothing is sold before announcing. Changing the date, hall or layout of a confirmed event sends it back to `submitted`. Tiers, prices and holds are the organizer's alone; the venue doesn't approve them. **Rescheduling:** changing an announced event's times keeps it announced and its tickets valid, sets `rescheduled_at`, and is checked by the no-overlap rule; from M2 the venue manager agrees to the new date. "Postponed, date not known yet" is left out (a known limit). **Why:** venue-based ticketing works this way: the promoter and the venue agree on a date first (venues keep a calendar of holds), and the promoter then decides when to announce and open sales; the venue cares about its calendar, room and capacity, not prices. From M2 a venue's own events (a cinema's showings) are confirmed on submit. "On sale", "sold out" and "past" stay derived. **Drafts don't take the slot:** the exclusion constraint has `WHERE (status IN ('submitted', 'confirmed', 'announced'))`, so drafts can share a date and the submit itself claims the slot (a second submit for it is refused with `23P01`, however close together they come). **Simplification:** real venues rank several tentative holds on one date; here one event at a time can be submitted for a slot. **Changeover time:** optional `hall_reserved_from` / `hall_reserved_until` (setting up before, clearing after) are what the no-overlap rule compares (`coalesce` falls back to the show's times), so customers still see the show's own `starts_at` and `ends_at`; columns rather than an interval, since `timestamptz + interval` isn't allowed in an index expression (it depends on the time zone setting). **Sales close** at `off_sale_at` (optional, after `on_sale_at`, at the end at the latest; empty means at the start), so online sales can stop before the start or run on for late entry. **Passes** use the same names without the venue's steps (`draft`, `announced`, `cancelled`); the events' sales times are for single tickets only, so a pass is sold by its own `on_sale_at` while every event it covers is announced and none has started, and can go on sale weeks before the day tickets. |

| 2026-11-23 | **A milestone in several pull requests.** One branch per milestone made M1 one pull request of over 11,000 lines (about half of them tests) before any endpoint past venues, too much to review at once. A milestone can now merge into `main` in parts, each its own branch `milestone/{milestone name}-{part}` and its own pull request, and **each part ends with `go test -race` green and CI passing**, so `main` always works. (Git can't have `milestone/postgres-event` and `milestone/postgres-event/…` at once, as it stores branch names like file paths, hence the hyphen.) | 2026-11-24 | **Locks follow the tree: parent before child.** A change to a child row (a hall now; layouts, sections and seats as they are built) locks its parent `FOR SHARE` first and then the child `FOR UPDATE`, never the other way round. Deleting a parent locks the parent and then, through `ON DELETE CASCADE`, its children; a change that held the child while waiting for the parent would deadlock with it (Postgres would cancel one with SQLSTATE `40P01`). The child's parent id is read without a lock first, which is safe because a child never moves to another parent. Tested deterministically: another transaction holds the venue, and the hall must still be free while the change waits. **What the parent lock is for:** checking the parent is active and keeping it so until the commit (a hall of an archived venue counts as archived, so its changes are refused with "venue is archived: restore it first"). Reads, lists and deletes of a child take no parent lock: they don't depend on the parent's state, and a child of an archived parent can be deleted, as an archived child can. **An archived parent is refused before the child's version is checked** (and before the child is locked): the child's ETag covers only its own values, and archiving the parent doesn't change it, so a 412 would send the caller to read the child again only to get the 409 next. The child's own status still comes after its version, as for venues: archiving the child changes its version. |
| 2026-11-27 | **Layout statuses** (M1 step 6c, built). `draft` → **activate** → `active`; `draft` or `active` → **archive** → `archived`; **restore** → always `draft`. **Activate needs at least one section**, since an event is sold in its sections (the check runs with the layout locked `FOR UPDATE`, and section changes will lock their layout first, M1 step 6d, so the last section can't go between the check and the commit; step 7 may add that every seated section has a seat). **Restore is always a draft, not the status before archiving:** no column to remember it (migration 3 is on `main`), nothing is offered for events again without a deliberate activate that runs its checks again, and a layout's own status isn't written when its hall or venue is archived, so restoring them already brings layouts back exactly as they were; archive and restore is also how an active layout that isn't frozen gets back to draft to fix a section until events exist. **PATCH** changes a draft's or active layout's name and description (labels; what is sold is in the sections, frozen once a confirmed event uses the layout, M1 step 11). The list defaults to `active`, as for halls; `?status=draft` lists the layouts being set up. |
