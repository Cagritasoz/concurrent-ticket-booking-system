# 05 · Decisions

A log of the decisions that shape the project. Open decisions list the recommended option and the
milestone in which they will be settled.

## Made

| Date | Decision |
|---|---|
| 2026-10-14 | Module path `github.com/Cagritasoz/concurrent-ticket-booking-system`. |
| 2026-10-14 | The early learning code was moved to `examples/` (see [09-examples](09-examples.md)). |
| 2026-10-14 | Postgres is added in M1, not M0, to keep the foundation small. |
| 2026-10-20 | One branch per milestone, named `milestone/{milestone name}`, branched from `main`. |
| 2026-10-20 | M0: tests are written in each step, not saved for the end. |
| 2026-10-20 | Environment variables have no project prefix (`HTTP_ADDR`, `LOG_LEVEL`, ...). The default port is `8080`. |
| 2026-10-20 | No `.env` loading library (such as godotenv). The app reads plain environment variables with defaults; locally a `.env` file is passed to the process by the IDE's .env plugin. `.env` is ignored by git. |
| 2026-10-20 | Tooling: GNU `make` (on Windows from MSYS2) for the Makefile, `golangci-lint` v2 for linting. No cross-platform task-runner alternative. |
| 2026-10-20 | Test runs (local and CI) cover only the application code, `./cmd/... ./internal/... ./migrations/...` (`./migrations/...` added 2026-11-17). `examples/` is left untouched and its tests are run by hand only. |
| 2026-10-20 | `.idea/` is not tracked by git. |
| 2026-10-21 | Logs carry a request ID: a valid incoming `X-Request-ID` is reused, otherwise a UUID is generated. It is stored in the request context and added to every log line written with that context. |
| 2026-10-31 | The `http.Server` is created only after the listener is open, and closed by a deferred `Close()` on every exit path of `run`. Whoever creates a resource closes it; `serve` only uses the server it is given. |
| 2026-11-01 | Graceful shutdown order: mark not ready → `server.Shutdown` within `SHUTDOWN_TIMEOUT` → force-close what's left and exit 1 if the deadline passes. A second Ctrl+C exits immediately. No pause between "not ready" and `Shutdown` until a deployment behind a load balancer needs one. |
| 2026-11-01 | The system serves any kind of event (movie showings, concerts, festivals), seated and general admission alike. Every event is one dated occurrence at a venue; a movie shown 30 times is 30 events. |
| 2026-11-01 | Ticket tiers (e.g. Standard, Pro, Ultimate) start with a name, a price and a description. The design must make two later additions easy without reworking bookings: **tier rules that are enforced** (e.g. sales windows, presale codes, access zones) and **multi-event passes** (one purchase covering tickets in several events). Neither is built until it is needed. |
| 2026-11-01 | **Per-customer purchase limits** per tier (e.g. at most 4 Ultimate tickets per customer) are part of the booking rules (M3). |
| 2026-11-01 | **Inventory model:** Venue → Layout → Section (seated with seats, or standing with a capacity); Event (in one layout of its venue) → TicketTier (price, description; later rules) → **one `tickets` row per sellable unit**, linked to a seat for seated sections and to its standing section for general admission (updated 2026-11-17, see below). The tier decides the price, the seat decides the place. Invariant I1 then covers seated and general admission alike, and concurrent general-admission buyers lock different rows (`FOR UPDATE SKIP LOCKED`) instead of queuing on one hot `remaining` counter. Bookings separate *what was bought at what price* (booking lines: a tier ticket, later a pass) from *which inventory units are reserved* (booking items → tickets), so a multi-event pass is one line reserving tickets in several events. |
| 2026-11-01 | **Seat selection:** for seated tiers the customer picks specific seats and the booking reserves exactly those tickets; for general-admission tiers the customer picks a quantity and the booking reserves any free tickets of the tier. "Best available" for seated tiers is added only after the system is proven under load, e.g. 1,000 concurrent users booking the same seat with exactly one winner. |
| 2026-11-01 | **Per-customer limits are enforced** with a counter row per (customer, tier), updated in the same transaction as the booking, with a database `CHECK (count <= limit)`. Two parallel requests from the same customer can't both slip under the limit, and the rows are per customer, so they don't become hot rows. |
| 2026-11-03 | CI runs lint, tests with `-race` and a build on GitHub Actions, on pushes to `main` and `milestone/**` and on pull requests into `main`. The `golangci-lint` version is pinned (v2.15.0, the same as locally) and upgraded on purpose, because a new version can report new issues. |
| 2026-11-03 | Go files are always LF (`.gitattributes`). With `core.autocrlf=true`, switching branches on Windows could otherwise turn them into CRLF, which gofmt and so `make lint` report as unformatted. |
| 2026-11-03 | Postgres runs as `postgres:17.11-alpine`, with an exact version pin. Credentials in Compose are `${...}` placeholders filled from `.env`, and a `pg_isready` health check reports when it accepts connections. |
| 2026-11-03 | `DATABASE_URL` is required and has no default, because it contains a password. The app connects at startup and stops if it can't reach Postgres. |
| 2026-11-03 | The connection pool uses pgx's default settings. Pool settings are added around the M9 load tests, when there are numbers to base them on; until then, `pool_max_conns` can be set in the URL. |
| 2026-11-17 | The domain model aims for full realism: designs are compared with how real ticketing platforms model the same thing, and simplifications are written down as such. |
| 2026-11-17 | Migrations use golang-migrate: plain SQL, an up and a down file per change, embedded into the program from `migrations/`. sqlc (M1 step 4) reads the same folder as its schema, and the test Postgres (M1 step 3) applies it. A migration that was applied anywhere is never edited; changes get a new file. |
| 2026-11-17 | **Migrations run by an explicit command** (`make migrate-up`, i.e. `cmd/migrate`), not at app startup, so several starting instances can't race and a bad migration doesn't stop the app from booting by surprise. `down` rolls back one migration at a time, never all. A failed migration leaves the database "dirty"; it is fixed by hand and cleared with `force`. |
| 2026-11-17 | `cmd/migrate` opens the database connection itself (pgx through `database/sql`) instead of handing the URL to golang-migrate, so errors never contain the password and the connection check has a time limit. It reads the same environment variables as the app. |
| 2026-11-17 | Tests that need Postgres call `pgtest.NewDatabase` (or `NewMigratedDatabase`, with every migration applied), which creates a fresh database per test and drops it afterwards. |
| 2026-11-18 | **Test Postgres comes from Testcontainers** (testcontainers-go v0.45.0, `postgres:17.11-alpine` like Compose): one container per test package, started by the first test that needs it and removed by `pgtest.Main` in `TestMain`; Ryuk removes it if the process is killed. `TEST_DATABASE_URL` stays as an override for an existing server. `go test -short` skips these tests. When neither Docker nor `TEST_DATABASE_URL` is available the tests **fail**, they don't skip, so a missing database can't hide them. CI uses Testcontainers too. |
| 2026-11-17 | **Venues:** UUID primary keys (`gen_random_uuid()`) for every table the API exposes; name and optional description; an international address (line 1, optional line 2, city, optional region and postal code, ISO country code), the same shape Stripe uses; optional latitude and longitude, set together; an IANA time zone, so event times can be entered and shown in local time; an optional capacity (maximum occupancy), checked at publish. Optional text is `NULL`, never empty: the `CHECK`s reject blank strings. |
| 2026-11-17 | **Layouts:** a venue has several layouts (e.g. concert with a standing floor, basketball, theatre setup). A layout has sections, each either seated (with seats labelled by row and seat) or standing (with a capacity). Every event uses one layout of its venue; a venue with only standing room has a layout with one standing section, so there is no "venue without layout" case. Publishing checks that standing tickets fit their section's capacity and the total fits the venue's capacity. |
| 2026-11-19 | **sqlc v1.31.1** generates the Go code for queries, with pgx v5 as the driver. It is installed as a binary pinned to an exact version, like golangci-lint, not added to `go.mod` as a tool, so its many dependencies don't mix into the app's. The generated code is committed, so building and testing don't need sqlc; CI checks it is current with `sqlc diff`. Hand-written tests live next to it. |
| 2026-11-19 | **Generated Go types:** standard library types where they exist: `uuid.UUID` (Go's `uuid` package) for `uuid`, `time.Time` for `timestamptz`, pointers for nullable columns (`*string`, nil is `NULL`), and `*float64` for venue coordinates (map positions, not money, so float precision is fine). `:many` queries return an empty slice, never nil. |
| 2026-11-19 | **Transactions** go through `postgres.WithTx(ctx, pool, fn)`: commit when `fn` returns nil, roll back on an error or a panic, `fn`'s error returned unchanged. READ COMMITTED (Postgres's default); a read-change-write locks its rows with `SELECT ... FOR UPDATE`. |
| 2026-11-19 | **Database errors:** a broken constraint is recognised by SQLSTATE code and constraint name (`postgres.IsUniqueViolation`, `IsForeignKeyViolation`, `IsCheckViolation`), so each module maps its own constraints to its own errors; "not found" is `pgx.ErrNoRows`. The module errors themselves (e.g. venue not found) arrive with the services that return them (step 5). |
| 2026-11-19 | **Lists use keyset pagination** (`WHERE (sort key, id) > (last values) ORDER BY ... LIMIT`), not `OFFSET`: every page costs the same and rows added meanwhile don't shift pages. Venues are listed by name, then id, with an index on `(name, id)` (migration 2). |
| 2026-11-20 | **Module layers:** handler (`httpapi`) → service (e.g. `event.VenueService`) → sqlc queries → Postgres. No repository layer of our own: the generated `Queries` already is one, and Postgres code is tested against real Postgres, not mocks. |
| 2026-11-20 | **Services return the module's own types** (e.g. `event.Venue`), converted from the generated row in one function, so `httpapi` never imports a `...db` package and a new column doesn't change a service's API. Not found is a module error (`event.ErrVenueNotFound`), not `pgx.ErrNoRows`. |
| 2026-11-20 | **HTTP errors are RFC 9457 Problem Details** (`application/problem+json`, the format Spring Boot 3's `ProblemDetail` uses), the same for every endpoint; validation errors list each field's problem. **Validation errors are 400 Bad Request**, like malformed JSON; 500s carry no detail, which goes only to the log. Built in M1 step 5b. |
| 2026-11-20 | **Input validation lives in the service** (e.g. `event.VenueInput`), in plain Go, not in struct tags or the HTTP layer: every problem is reported at once as a `*event.ValidationError`, each with the field's path in the API's JSON (`address.city`). Text is trimmed; optional text that is empty after trimming becomes `NULL`, so `""` and a missing field mean the same. A `CHECK` that still fails in Postgres is a bug in our validation, so it is a 500, not a 400. Country codes are checked for their shape (two capital letters) only, not against the ISO list. |
| 2026-11-20 | **Time zones are checked with Go's IANA database**, which `cmd/ticketing` embeds (`time/tzdata`, about 450 KB), so it works where the system has none (Windows, minimal container images). |
| 2026-11-20 | **Request bodies are read strictly:** `Content-Type: application/json` (else 415), at most 64 KiB (else 413), unknown fields rejected and nothing after the object (400). The decoding error messages are our own, in JSON terms, because `encoding/json`'s name Go types. Create answers `201 Created` with a `Location` header. |
| 2026-11-20 | **List endpoints page with an opaque cursor:** `?limit=` (default 20, at most 100) and `?cursor=`, answered as `{"venues": [...], "next_cursor": "..." or null}`. The cursor is the last venue's sort values (name, id) as base64url JSON; clients only pass it back, so its contents can change. It is not signed: an edited cursor only starts the page elsewhere. The service fetches one row more than the limit, so `next_cursor` is null on the last page even when that page is full, and no total count is returned (it would need a count over the whole table on every page). Unknown query parameters are ignored, unlike unknown body fields. |
| 2026-11-21 | **Partial updates are PATCH with JSON Merge Patch** (RFC 7396, `application/merge-patch+json`; `application/json` is accepted too, since the body is the same). A field left out is kept, `null` clears it (a required field set to `null` is reported as missing), nested objects (`address`, `location`) are merged. No PUT. The body is first decoded as the create body, which gives the same checks and error messages, then into a type that records which fields were sent (`patchField`: left out / null / value). The service's `Update` takes a change function, applied to the current values inside the locked transaction, so the merge (an HTTP format) stays in `httpapi` and the rules, the lock and the write stay in `event`. Every successful PATCH sets `updated_at`, also one that changes nothing. |
| 2026-11-21 | **DELETE answers 204 No Content**, and 404 when no venue has the id, also for a second delete of the same venue. Deleting a venue that layouts or events use is a question for steps 6 and 8, when those tables reference venues. |

## Open

| Settle in | Topic | Recommendation |
|---|---|---|
| M1 step 7 | **Seat ordering** | Besides the row and seat labels (text, since real labels look like `AA` or `12A`), store integer row and seat positions, so seats sort correctly and "best available" can later find seats next to each other. |
| M1 step 10 | **When tickets are created** | At publish, in one transaction. Tiers stay freely editable while the event is a draft, with no ticket rows to keep in sync. |
| M1 step 11 | **What can change after publishing** | Only descriptive text (names, descriptions). Prices, quantities, seats and the date stay fixed; changing them means cancelling the event and creating a new one. A layout used by a published event is frozen; to change it, the admin copies it and edits the copy. |
| M3 | **Hold duration and anti-hoarding** | A short configurable hold time (around 10 minutes), at most one open booking per event per customer, and rate limiting on `POST /bookings`, on top of the per-customer limits. Details in [10 · System flows](10-system-flows.md#a-user-who-keeps-blocking-tickets). |
| M7 | **Customer-initiated refunds** | Not decided: whether customers may request refunds, and until when. Event cancellation always refunds. |
| M7 | **Late payment on an expired booking** | Pause expiry while a payment is processing. On a late success, reclaim the same tickets if they are still free, otherwise refund automatically. A possible later upgrade is Stripe authorize-then-capture (`capture_method=manual`). "Always refund" was rejected as needlessly unfriendly. |
| M9 | **Observability stack** | Prometheus (scraping `/metrics`) + Grafana in Docker Compose, added together with the k6 load tests. Loki and Tempo are not planned: logs are already JSON on stdout (ready for Loki if ever needed), and a single binary gains little from distributed tracing. |
