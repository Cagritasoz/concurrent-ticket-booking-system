# 05 · Decisions

A log of the decisions that shape the project. Open decisions list the recommended option and the
milestone in which they will be settled.

| 2026-10-20 | `.idea/` is not tracked by git. |
| 2026-10-21 | Logs carry a request ID: a valid incoming `X-Request-ID` is reused, otherwise a UUID is generated. It is stored in the request context and added to every log line written with that context. |
| 2026-10-31 | The `http.Server` is created only after the listener is open, and closed by a deferred `Close()` on every exit path of `run`. Whoever creates a resource closes it; `serve` only uses the server it is given. |
| 2026-11-01 | Graceful shutdown order: mark not ready → `server.Shutdown` within `SHUTDOWN_TIMEOUT` → force-close what's left and exit 1 if the deadline passes. A second Ctrl+C exits immediately. No pause between "not ready" and `Shutdown` until a deployment behind a load balancer needs one. |
| 2026-11-01 | The system serves any kind of event (movie showings, concerts, festivals), seated and general admission alike. Every event is one dated occurrence at a venue; a movie shown 30 times is 30 events. |
| 2026-11-01 | Ticket tiers (e.g. Standard, Pro, Ultimate) start with a name, a price and a description. The design must make two later additions easy without reworking bookings: **tier rules that are enforced** (e.g. sales windows, presale codes, access zones) and **multi-event passes** (one purchase covering tickets in several events). Neither is built until it is needed. |
| 2026-11-01 | **Per-customer purchase limits** per tier (e.g. at most 4 Ultimate tickets per customer) are part of the booking rules (M3). |
| 2026-11-01 | **Inventory model:** Venue → Layout → Section (seated with seats, or standing with a capacity); Event (in one layout of its venue) → TicketTier (price, description; later rules) → **one `tickets` row per sellable unit**, linked to a seat for seated sections and to its standing section for general admission (updated 2026-11-17, see below). The tier decides the price, the seat decides the place. Invariant I1 then covers seated and general admission alike, and concurrent general-admission buyers lock different rows (`FOR UPDATE SKIP LOCKED`) instead of queuing on one hot `remaining` counter. Bookings separate *what was bought at what price* (booking lines: a tier ticket, later a pass) from *which inventory units are reserved* (booking items → tickets), so a multi-event pass is one line reserving tickets in several events. |
| 2026-11-01 | **Seat selection:** for seated tiers the customer picks specific seats and the booking reserves exactly those tickets; for general-admission tiers the customer picks a quantity and the booking reserves any free tickets of the tier. "Best available" for seated tiers is added only after the system is proven under load, e.g. 1,000 concurrent users booking the same seat with exactly one winner. |
| 2026-11-01 | **Per-customer limits are enforced** with a counter row per (customer, tier), updated in the same transaction as the booking, with a database `CHECK (count <= limit)`. Two parallel requests from the same customer can't both slip under the limit, and the rows are per customer, so they don't become hot rows. |
| 2026-11-03 | CI runs lint, tests with `-race` and a build on GitHub Actions, on pushes to `main` and `milestone/**` and on pull requests into `main`. The `golangci-lint` version is pinned (v2.15.0, the same as locally) and upgraded on purpose, because a new version can report new issues. |
| 2026-11-03 | Go files are always LF (`.gitattributes`). With `core.autocrlf=true`, switching branches on Windows could otherwise turn them into CRLF, which gofmt and so `make lint` report as unformatted. |
| 2026-11-03 | Postgres runs as `postgres:17.11-alpine`, with an exact version pin. Credentials in Compose are `${...}` placeholders filled from `.env`, and a `pg_isready` health check reports when it accepts connections. |
| 2026-11-03 | `DATABASE_URL` is required and has no default, because it contains a password. The app connects at startup and stops if it can't reach Postgres. |
| 2026-11-03 | The connection pool uses pgx's default settings. Pool settings are added around the M9 load tests, when there are numbers to base them on; until then, `pool_max_conns` can be set in the URL. |
| 2026-11-17 | The domain model aims for full realism: designs are compared with how real ticketing platforms model the same thing, and simplifications are written down as such. |
| 2026-11-17 | Migrations use golang-migrate: plain SQL, an up and a down file per change, embedded into the program from `migrations/`. sqlc (M1 step 4) reads the same folder as its schema, and the test Postgres (M1 step 3) applies it. A migration that was applied anywhere is never edited; changes get a new file. (Updated 2026-11-22: see "Migrations are edited until their milestone merges" below.) |
| 2026-11-17 | **Migrations run by an explicit command** (`make migrate-up`, i.e. `cmd/migrate`), not at app startup, so several starting instances can't race and a bad migration doesn't stop the app from booting by surprise. `down` rolls back one migration at a time, never all. A failed migration leaves the database "dirty"; it is fixed by hand and cleared with `force`. |
| 2026-11-17 | `cmd/migrate` opens the database connection itself (pgx through `database/sql`) instead of handing the URL to golang-migrate, so errors never contain the password and the connection check has a time limit. It reads the same environment variables as the app. |
| 2026-11-17 | Tests that need Postgres call `pgtest.NewDatabase` (or `NewMigratedDatabase`, with every migration applied), which creates a fresh database per test and drops it afterwards. |
| 2026-11-18 | **Test Postgres comes from Testcontainers** (testcontainers-go v0.45.0, `postgres:17.11-alpine` like Compose): one container per test package, started by the first test that needs it and removed by `pgtest.Main` in `TestMain`; Ryuk removes it if the process is killed. `TEST_DATABASE_URL` stays as an override for an existing server. `go test -short` skips these tests. When neither Docker nor `TEST_DATABASE_URL` is available the tests **fail**, they don't skip, so a missing database can't hide them. CI uses Testcontainers too. |
| 2026-11-17 | **Venues:** UUID primary keys (`gen_random_uuid()`) for every table the API exposes; name and optional description; an international address (line 1, optional line 2, city, optional region and postal code, ISO country code), the same shape Stripe uses; optional latitude and longitude, set together; an IANA time zone, so event times can be entered and shown in local time; an optional capacity (maximum occupancy), checked at publish. Optional text is `NULL`, never empty: the `CHECK`s reject blank strings. (Updated 2026-11-22: the capacity moved to halls; venues gained a status and a version, see below.) |
| 2026-11-17 | **Layouts:** a venue has several layouts (e.g. concert with a standing floor, basketball, theatre setup). A layout has sections, each either seated (with seats labelled by row and seat) or standing (with a capacity). Every event uses one layout of its venue; a venue with only standing room has a layout with one standing section, so there is no "venue without layout" case. Publishing checks that standing tickets fit their section's capacity and the total fits the venue's capacity. (Updated 2026-11-22: layouts belong to a hall of the venue, and the total is checked against the hall's capacity, see below.) |
| 2026-11-19 | **sqlc v1.31.1** generates the Go code for queries, with pgx v5 as the driver. It is installed as a binary pinned to an exact version, like golangci-lint, not added to `go.mod` as a tool, so its many dependencies don't mix into the app's. The generated code is committed, so building and testing don't need sqlc; CI checks it is current with `sqlc diff`. Hand-written tests live next to it. |
| 2026-11-19 | **Generated Go types:** standard library types where they exist: `uuid.UUID` (Go's `uuid` package) for `uuid`, `time.Time` for `timestamptz`, pointers for nullable columns (`*string`, nil is `NULL`), and `*float64` for venue coordinates (map positions, not money, so float precision is fine). `:many` queries return an empty slice, never nil. |
| 2026-11-19 | **Transactions** go through `postgres.WithTx(ctx, pool, fn)`: commit when `fn` returns nil, roll back on an error or a panic, `fn`'s error returned unchanged. READ COMMITTED (Postgres's default); a read-change-write locks its rows with `SELECT ... FOR UPDATE`. |
| 2026-11-19 | **Database errors:** a broken constraint is recognised by SQLSTATE code and constraint name (`postgres.IsUniqueViolation`, `IsForeignKeyViolation`, `IsCheckViolation`), so each module maps its own constraints to its own errors; "not found" is `pgx.ErrNoRows`. The module errors themselves (e.g. venue not found) arrive with the services that return them (step 5). |
| 2026-11-19 | **Lists use keyset pagination** (`WHERE (sort key, id) > (last values) ORDER BY ... LIMIT`), not `OFFSET`: every page costs the same and rows added meanwhile don't shift pages. Venues are listed by name, then id, one status at a time, with an index on `(status, name, id)` (migration 1). |
| 2026-11-20 | **Module layers:** handler (`httpapi`) → service (e.g. `event.VenueService`) → sqlc queries → Postgres. No repository layer of our own: the generated `Queries` already is one, and Postgres code is tested against real Postgres, not mocks. |
| 2026-11-20 | **Services return the module's own types** (e.g. `event.Venue`), converted from the generated row in one function, so `httpapi` never imports a `...db` package and a new column doesn't change a service's API. Not found is a module error (`event.ErrVenueNotFound`), not `pgx.ErrNoRows`. |
| 2026-11-20 | **HTTP errors are RFC 9457 Problem Details** (`application/problem+json`, the format Spring Boot 3's `ProblemDetail` uses), the same for every endpoint; validation errors list each field's problem. **Validation errors are 400 Bad Request**, like malformed JSON; 500s carry no detail, which goes only to the log. Built in M1 step 5b. |
| 2026-11-20 | **Input validation lives in the service** (e.g. `event.VenueInput`), in plain Go, not in struct tags or the HTTP layer: every problem is reported at once as a `*event.ValidationError`, each with the field's path in the API's JSON (`address.city`). Text is trimmed; optional text that is empty after trimming becomes `NULL`, so `""` and a missing field mean the same. A `CHECK` that still fails in Postgres is a bug in our validation, so it is a 500, not a 400. Country codes are checked for their shape (two capital letters) only, not against the ISO list. |
| 2026-11-20 | **Time zones are checked with Go's IANA database**, which `cmd/ticketing` embeds (`time/tzdata`, about 450 KB), so it works where the system has none (Windows, minimal container images). |
| 2026-11-20 | **Request bodies are read strictly:** `Content-Type: application/json` (else 415), at most 64 KiB (else 413), unknown fields rejected and nothing after the object (400). The decoding error messages are our own, in JSON terms, because `encoding/json`'s name Go types. Create answers `201 Created` with a `Location` header. |
| 2026-11-20 | **List endpoints page with an opaque cursor:** `?limit=` (default 20, at most 100) and `?cursor=`, answered as `{"venues": [...], "next_cursor": "..." or null}`. The cursor is the last venue's sort values (name, id) as base64url JSON; clients only pass it back, so its contents can change. It is not signed: an edited cursor only starts the page elsewhere. The service fetches one row more than the limit, so `next_cursor` is null on the last page even when that page is full, and no total count is returned (it would need a count over the whole table on every page). Unknown query parameters are ignored, unlike unknown body fields. |
| 2026-11-21 | **Partial updates are PATCH with JSON Merge Patch** (RFC 7396, `application/merge-patch+json`; `application/json` is accepted too, since the body is the same). A field left out is kept, `null` clears it (a required field set to `null` is reported as missing), nested objects (`address`, `location`) are merged. No PUT. The body is first decoded as the create body, which gives the same checks and error messages, then into a type that records which fields were sent (`patchField`: left out / null / value). The service's `Update` takes a change function, applied to the current values inside the locked transaction, so the merge (an HTTP format) stays in `httpapi` and the rules, the lock and the write stay in `event`. Every successful PATCH sets `updated_at`, also one that changes nothing. (Updated 2026-11-22: a PATCH also needs `If-Match` and raises the version, see below.) |
| 2026-11-21 | **DELETE answers 204 No Content**, and 404 when no venue has the id, also for a second delete of the same venue. Deleting a venue that layouts or events use is a question for steps 6 and 8, when those tables reference venues. (Updated 2026-11-22: DELETE needs `If-Match`, and is meant for what nothing uses; used objects are archived, see below.) |
| 2026-11-22 | **Halls between venue and layout:** venue → hall → layout → section. A venue is the building (address, time zone); a hall is a room in it that can host events at the same time as the other halls (a cinema's screens, a convention center's halls, an arena's one main floor); a layout is one way to set up a hall, one at a time. A venue with one room has one hall. A hall has a name, an optional description and an optional capacity, the room's maximum occupancy; publishing an event (M1 step 10) checks its tickets against its hall's capacity. **The venue has no capacity of its own**: it would repeat what its halls say (a one-room venue's capacity is its hall's), and a building-wide limit across halls running at once is not something ticketing systems enforce. Ticketmaster and Eventbrite instead list each room as its own venue; cinema systems (e.g. Vista: cinema → screens) model rooms explicitly, which is what we need to serve cinemas and multi-room buildings, where one building's events should be found together and its address kept once. |
| 2026-11-22 | **Frontend:** TypeScript + React, built after M2 (both UIs need login): an admin UI first, then a customer UI that grows with M3 onward. The owner decides how it looks and works; Claude writes the code. The seat map is our own, drawn from our seat data, not a third-party service such as Seats.io: Seats.io also keeps each seat's status per event, which would be a second source of truth for exactly what this system exists to get right (holds and exactly one winner per seat). When the frontend runs on another origin, CORS must allow the `If-Match` request header and expose the `ETag` response header, or the browser hides it from the code. |
| 2026-11-22 | **Roles and ownership, Ticketmaster-style** (built in M2). Three roles: **venue managers** build and maintain venue maps (venue, halls, layouts, sections, seats) and set event-level kills, which depend on the room; **organizers** (promoters) create and run events, tiers, prices and publishing, and set admin holds (artist, sponsors, press); **customers** book. Both admin sides are companies, not single people, so M2 adds **organizations** (`venue_operator` or `organizer`) with **memberships** (a Keycloak user and their role in the organization). A venue belongs to one operator organization (`venues.operator_id`), and its managers see and change only their own venues. **A venue grants an organizer access** (`venue_access`: venue, organizer, granted by, granted at, revoked at) before the organizer's staff can create events in its active layouts; revoking blocks new events, existing ones stay. An event belongs to its organizer (`events.organizer_id`). Keycloak keeps identities and global roles; organizations, memberships and grants are business data in our database, checked by the services (I13). **Simplification:** real venues grant dates (a calendar of holds on dates), not the whole venue. Until M2 the admin API is open and these columns don't exist; M2 adds them by editing the M1 migrations if M1 isn't merged yet, otherwise with new migrations. |
| 2026-11-22 | **Lifecycle: archive instead of deleting what was used** (like Stripe products or GitHub repositories). Venues and halls are `active` or `archived`; layouts `draft`, `active` or `archived` (a layout is built over many requests and can't be chosen for an event until it is activated). **`DELETE` really deletes, only what nothing uses**; once events exist, their foreign keys (without cascade) refuse it, and the service answers 409 "archive it instead". **Archive and restore** are their own requests (`POST /{resource}/{id}/archive`, `/restore`), not a `status` field in PATCH, like Google's API design guide's custom methods. An archived object stays for history (past events, tickets and refunds point at it), is hidden from the default list (`?status=archived` lists them), can't be changed and gets no new children; archiving is refused while upcoming events depend on it (M1 step 8). Status changes are **compare-and-set** statements (`UPDATE ... WHERE id = $1 AND version = $2 AND status = 'active'`): when nothing matched, the service reads the row once to say why (not found, other version, wrong status). The children of an archived parent count as archived without their own rows being written. Creating a child reads and locks its parent (`SELECT ... FOR SHARE`) to check it is active. Name uniqueness ignores archived rows (partial unique indexes, `WHERE status <> 'archived'`), so a name can be reused. **Sections and seats have no status:** they are part of their layout's definition, edited while it is a draft. A layout used by a published event is frozen; "frozen" is derived from the events, not stored. Built for venues; halls, layouts and the rest follow as they are built. |
| 2026-11-22 | **Optimistic locking with ETags on every admin change** (like JPA's `@Version`). Every table an admin changes has `version integer NOT NULL DEFAULT 1`, raised by 1 on every change (not `updated_at`, which repeats within a transaction, and not Postgres's internal `xmin`). Responses with one object send it as a strong `ETag` (`"3"`); lists carry `version` in each item instead. PATCH, DELETE, archive and restore **require** `If-Match` with that ETag: another version is `412 Precondition Failed` (read again, redo the change), a missing header or `*` is `428 Precondition Required` (a change must name what it is based on; `*` would mean "overwrite whatever is there"), and anything that isn't one ETag as the API sends it (unquoted, weak `W/`, a list) is `400`. Creates need none. Each object has its own version: changing a section doesn't raise its layout's. Requiring the header is stricter than most public APIs (Azure and Google Cloud make it optional; Kubernetes requires a `resourceVersion` on updates); it fits an internal admin API whose one client, our UI, always has the version. In the service, the version check protects a person's edit; the row lock (`FOR UPDATE`) still protects the read-change-write inside one request. |
| 2026-11-22 | **Migrations are edited until their milestone merges into `main`**, then never again; later changes get new files. Before the merge only throwaway databases (tests, CI, a developer's local volume, which is recreated) have run them, and a table's whole structure stays readable in one file: migration 1 is the venues table with its index. |

## Open

| Settle in | Topic | Recommendation |
|---|---|---|
| M1 step 7 | **Seat ordering** | Besides the row and seat labels (text, since real labels look like `AA` or `12A`), store integer row and seat positions, so seats sort correctly and "best available" can later find seats next to each other. |
| M1 step 7 | **Seat attributes** | Every seat has a type: `standard`, `wheelchair` (a space for a wheelchair, often without a fixed seat) or `companion` (next to a wheelchair space, for a companion), plus flags for a restricted or obstructed view (with an optional note, e.g. "pillar") and an aisle seat. Real platforms show these on the seat map and in filters, and accessible seating has legal rules (e.g. the ADA in the US), so it is part of the layout, not left out. Which tiers may sell accessible seats, and releasing unsold ones to general sale before the event, are tier rules (M1 step 9 and later). |
| M1 steps 10–11 | **Event-level holds and kills** | Per event, not per layout, because the same layout hosts different productions: **a kill** removes a seat or standing places from sale for good (a camera position, the sound desk, a seat a stage blocks); **a hold** keeps tickets out of public sale for a named reason (artist, promoter, sponsor, press, accessible reserve) until an admin releases them to sale or books them for that party. Both work on the event's ticket rows (a status per ticket, and a holds table with a name and reason), so the tickets keep their seat and tier, and a release is one update. Changing them takes the same locks as other admin edits (I14), so a held or killed ticket can't be in a booking at the same time. Called **admin holds** in the code and docs, so they aren't confused with the short customer holds of M3 and M5. |
| M1 step 10 | **When tickets are created** | At publish, in one transaction. Tiers stay freely editable while the event is a draft, with no ticket rows to keep in sync. |
| M1 step 11 | **What can change after publishing** | Only descriptive text (names, descriptions). Prices, quantities, seats and the date stay fixed; changing them means cancelling the event and creating a new one. A layout used by a published event is frozen; to change it, the admin copies it and edits the copy. |
| M5 / M9 | **Caching hot events in Redis** | Cache what rarely changes and is read by everyone: a published event's details, tiers and prices, and its seat map's shape (only descriptive text can change after publishing). Cache-aside with a short expiry, deleted when an admin edits the event. Seat availability changes every second during an on-sale, so it is not cached the same way; it stays a Postgres read (or a Redis-backed counter) until M9's load tests show it needs more. Like holds, the cache is never the source of truth. |
| Frontend | **Real-time seat updates** | Push seat changes (taken, freed) to open seat maps over WebSockets (the owner wants them considered; Server-Sent Events are the one-way alternative). With several app instances each one must hear every change, through Redis pub/sub (M5) or Postgres `LISTEN/NOTIFY`. Updates only improve what the user sees: correctness still comes from the booking, where a seat taken meanwhile is refused. |
| M3 | **Hold duration and anti-hoarding** | A short configurable hold time (around 10 minutes), at most one open booking per event per customer, and rate limiting on `POST /bookings`, on top of the per-customer limits. Details in [10 · System flows](10-system-flows.md#a-user-who-keeps-blocking-tickets). |
| M7 | **Customer-initiated refunds** | Not decided: whether customers may request refunds, and until when. Event cancellation always refunds. |
| M7 | **Late payment on an expired booking** | Pause expiry while a payment is processing. On a late success, reclaim the same tickets if they are still free, otherwise refund automatically. A possible later upgrade is Stripe authorize-then-capture (`capture_method=manual`). "Always refund" was rejected as needlessly unfriendly. |
| M9 | **Observability stack** | Prometheus (scraping `/metrics`) + Grafana in Docker Compose, added together with the k6 load tests. Loki and Tempo are not planned: logs are already JSON on stdout (ready for Loki if ever needed), and a single binary gains little from distributed tracing. |
